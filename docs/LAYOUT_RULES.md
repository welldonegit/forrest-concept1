# Правила вёрстки FORREST

Как переносить выгрузку из Claude Design в проект. Стек, заявки и языки описаны в `CLAUDE.md`, порядок работ — в `docs/ROADMAP.md`. Этот файл отвечает на вопрос «как верстать».

# Задача

В `design-export/` лежит проект, сгенерированный в Claude Design: `index.html`, папки `components/`, `tokens/`, `assets/`, `vendor/`, скрипты `_ds_bundle.js`, `ds-base.js`, `image-slot.js` и фото. Это эталон: файлы в этой папке не правим, новый код пишем в `src/`. Нужно переписать его в компоненты Astro + чистый CSS + модули JS: разделить разметку, стили и логику, привести размеры и типографику к единой шкале, вынести весь контент в Sanity.

Визуал менять нельзя: расхождения не больше 2px на элемент.

Главное правило: **ничего не придумывай.** В проект попадает только то, что есть в выгрузке: секции, тексты, иконки, состояния, анимации. Чего-то не хватает (состояния ховера, мобильной версии блока, текста ошибки) — ставь `TODO:` и спрашивай. Не дорисовывай по аналогии.

Важный контекст: это боевой лендинг на 20 блоков, который будет переведён на 10+ языков, редактируется из админки и должен набирать 90+ в PageSpeed на мобильном. Поэтому чистота разметки и целые значения здесь не вопрос вкуса: от них зависят скорость, переводы без поломок и то, сможет ли редактор менять контент без разработчика.

# Решения аудита (Р1–Р8)

Источник истины по значениям — реальный рендер выгрузки (далее «рендер»): computed-стили `design-export/index.html`, снятые в headless-браузере на опорных ширинах (1920/1440/1024/390). Файлы `design-export/tokens/*.css` и `components/components.css` (чистые токены генератора) рендеру не соответствуют: из них берём только имена ролей, структуру токенов и палитру из 10 примитивов. Значения радиусов, размеров шрифта и отступов из токенов генератора не используем. (Р1)

- **Радиусы и отступы** — дискретные ступени из рендера; шкалы заданы ниже (Р2 — радиусы, Р4 — отступы). `clamp()` убираем везде: размеры дискретные по брейкпоинтам, в каждом брейкпоинте значение из шкалы (Р3). Какое значение брать на каждой ступени — см. «Диапазоны и контейнер».
- **Шкалы собираем по всей странице**, кроме скрытых вариантов (секции с `hidden`/`display:none`: Worlds Collage, Infra 8, Numbers/Calculator-варианты, Team hidden, Location без карты). Они общие для всех блоков. Видимые дубли (Construction B, Team v2/v3) в сбор шкал входят; какая версия каноническая — решение отложено (Р7).
- **Декоративный мок «Investor Dashboard»** (секция Investor Service) — иллюстрация с vw-текстом 3–10px и круглыми формами; его внутренние размеры в шкалы не входят.
- **Источник медиа** — `design-export/assets/photos/`; байт-в-байт дубли из корня, неиспользуемые файлы и тяжёлые PNG-дубли в сборку не идут (Р8).

## Диапазоны и контейнер

Брейкпоинты проекта — **1600, 1280, 768**. Выгрузка использует больше точек (767, 900/899, 600, 700, 640, 1023 и др.) для внутренних перестроений компонентов; их поведение переносим, но единые брейкпоинты проекта — эти три.

- **Отдельного контейнера нет (п.1).** Страница ограничена шириной **1920** вместе с боковыми полями секций: до 1920 раскладка как в выгрузке (контент на всю ширину минус поля), шире 1920 контент центрируется, а фоны и полноэкранные медиа идут на всю ширину.
- **Боковые поля секций (п.2):** на десктопе — из рендера, по шкале отступов; на мобильном — **20px** (осознанное изменение относительно выгрузки, там 16). При сверке на 390 это известное отличие: переносы строк из-за него показывай списком, не подгоняй.
- **Десктоп делится на две ступени:** `1280–1599` берёт значения из рендера на **1440**, `≥1600` — из рендера на **1920**. Это касается размеров шрифта и всего, что в выгрузке задано через `clamp()`/`vw`.
- **768–1279:** страница не ломается и читается; попиксельная сверка с выгрузкой не требуется. Опорная ширина проверки — **1024**. Перестроения компонентов на 900/600 и прочие между 768 и 1279 переносим как есть (п.3).
- **Мобильный (<768):** опорная ширина — **390**, дополнительная проверка на **360** (ничего не вылезает и не обрезается).

# Этап 1. Аудит (ничего не меняй, только отчёт)

Соответствует этапу 1 в `docs/ROADMAP.md`.

1. Инвентаризация стилей: где что живёт — инлайн, style-атрибуты, утилити-классы, `<style>`, дубли.
2. Все числовые значения размеров: width/height/min/max, padding, margin, gap, border-radius, border-width, размеры иконок, top/left/right/bottom, translate.
3. Вся типографика: font-size, line-height, font-weight, letter-spacing — с указанием, где значение задано напрямую, а где через clamp(), calc(), модульную шкалу или em от родителя.
4. Сведи в таблицу: значение → частота → где. Отдельно выдели дробные (13.5px, 31.56px, 1.953rem) и нечётные (7, 15, 23).
5. Инвентаризация JS: какие скрипты и библиотеки подключены, что делает каждый. Отдельно разбери служебные файлы генератора (`_ds_bundle.js`, `ds-base.js`, `image-slot.js`, папка `vendor/`): что из этого рантайм Claude Design, который в проект не переносится, а что реальная логика страницы. Раздели на три группы: логика интерфейса (меню, попапы, табы, аккордеон, слайдеры, форма), анимации, всё остальное.
6. Таблица анимаций по блокам: блок → элемент → что происходит → триггер (загрузка, появление, скролл, ховер, клик) → какие CSS-свойства меняются → длительность → easing → задержка. Отдельно отметь анимации, которые меняют не `transform` и `opacity` (width, height, top, left, margin, clip-path, filter).
7. Инвентаризация контента: все тексты, фото, видео, ссылки, телефоны. По каждому блоку — список будущих полей Sanity. Отдельно: тексты, зашитые в картинки, SVG или псевдоэлементы.
8. Медиа: список файлов с размерами в пикселях и весом. Отметь файлы тяжелее 25 MiB и фото, которые шире, чем нужно их контейнеру.
9. Отдельным списком — всё, что мешает скорости, переводам или админке:
   - фиксированные высоты и ширины у блоков с текстом;
   - абсолютное позиционирование для раскладки;
   - transform для раскладки;
   - `background-image` вместо `<img>` у контентных фото;
   - текст, разорванный на span-ы;
   - fluid-типографика;
   - иконочные шрифты;
   - тяжёлые эффекты (`backdrop-filter`, большие тени, `filter` на крупных областях).
10. Покажи мне таблицу маппинга «старое → новое» ПЕРЕД любыми правками. Значения, которые не ложатся на шкалу без сдвига больше 2px, вынеси отдельно и спроси меня. Отдельно — список текстовых элементов, у которых размер шрифта поехал больше чем на 2px после округления (риск другого переноса строк в узких контейнерах).
11. Список внутренних несоответствий выгрузки: одна роль с разными значениями в разных блоках, цвета вне палитры из `tokens/`. Не выбирай сам, какое значение верное.
12. Предложение по шкалам радиусов и размеров шрифта с вопросами ко мне — по порядку из раздела «Как собрать шкалу» (этап 2).

# Этап 2. Шкала размеров

Базовая шкала отступов и размеров (решения Р4 + п.11):
2, 4, 6, 8, 10, 12, 16, 20, 24, 28, 32, 36, 40, 44, 48, 56, 64, 72, 80, 96, 128

Мелкий конец — шаг 2px (2, 4, 6, 8, 10, 12), дальше шаг 4px (12…48), дальше шаг 8px (48, 56, 64, 72, 80), затем 96 и 128. 2px — только хайрлайны и микро-отступы.

- значение снимаем из рендера и приводим к ближайшей ступени шкалы;
- сдвиг не больше 2px; где больше — выноси в маппинг и спрашивай, молча не округляй.

Правило «всегда вниз» отменено (п.12). Значения **14, 18, 22, 26, 30, 34** в шкалу не входят — округляй к соседней ступени (±2px), направление выбирай так, чтобы итоговый габарит элемента (ширина и высота) изменился не больше чем на 2px. То есть если округление отступов с двух сторон суммарно уводит габарит больше 2px — часть округляй вверх, часть вниз.

Крупные промежутки **52, 84.5, 90, 140, 210, 441** разбираем поблочно при вёрстке, ступенями в шкалу не вносим (п.13).

Отдельные шкалы:

- border-radius: шкала (решения Р2 + п.14) — **0, 4, 12, 16, 20, 24, 28, 32, 40, pill**. `pill` — полноценный токен. 40 — рамка Hero (приёмка 4.1: прежнее «рамка Hero → 32» отменено, оно опиралось на неверное значение рендера). Маппинг: 2→4, 6→4; радиус 36 → 32; 14/18/22 → ближайшая ступень по роли элемента (как у соседних элементов той же роли); элемент с радиусом 2 тоньше 8px → pill. `50%`/`999px` → pill **только для однострочных полей и круглых контролов**; для `textarea` и других высоких элементов бери ступень из шкалы, чтобы скругление углов не изменилось больше чем на 2px (п.15). Сдвиг больше 2px недопустим — в маппинг и спросить;
- border-width: 1, 2;
- размеры иконок: **12**, 16, 20, 24, 32, 40 (12 — шеврон переключателя языка в Header, утверждено при приёмке 4.0);
- высоты контролов (кнопки, инпуты, чипы): 24, 32, 40, **44**, 48, 56, **60, 64** — задаются как `min-height`, одинаковые для элементов одного типа (44 — ступень tap-target, п.9; 60 и 64 — CTA Hero, приёмка 4.1). Ширина по содержимому: перевод может быть на 40% длиннее. Круглая иконочная кнопка Hero (72px) — иконочный размер, не контрол. Текстовые ссылки `min-height` не навязываем — габарит от шрифта и паддинга.
- где визуальная высота контрола на мобильном меньше 44px (например, Season CTA ~29px) — внешний вид не меняем, область нажатия расширяем до 44px прозрачным увеличением зоны (`::before`/паддинг), без изменения вида (п.10).

Не трогаем: проценты, vh/vw, fr, minmax(), auto, aspect-ratio, 1px границы, длительности и easing анимаций.

**Собственные размеры элементов (приёмка 4.1).** Шкала отступов относится только к `padding`, `margin` и `gap`. Собственные размеры элементов — ширина и высота кнопок, иконок, логотипов, колонок, декоративных фигур — берутся из рендера на опорных ширинах с округлением до целого и утверждения не требуют. Спрашивать только если отклонение от рендера на опорной ширине больше 2px. Шкалы контролов, иконок и радиусов при этом действуют: если ступень шкалы даёт отклонение ≤2px — берём ступень.

Если отступы в выгрузке системно не совпадают со шкалой (например, везде 6px) — не округляй молча, вынеси в маппинг и спроси.

## Как собрать шкалу

Шкала радиусов задана решением Р2 (выше). Шкала размеров шрифта выводится из рендера и согласуется со мной: computed `font-size`/`line-height` на опорных ширинах, сгруппированные в ступени; имена ролей — из Системы А там, где значение совпадает в пределах 2px. 15px — отдельная ступень, 13 и 17 не сводим. Декоративные цифры (144/200px) — отдельная декоративная ступень вне текстовой шкалы. Цель — система, а не список всего, что встретилось. Порядок:

1. Выпиши все значения из выгрузки: значение → сколько раз встречается → в каких элементах и ролях.
2. Сгруппируй близкие значения (в пределах 2px) и предложи для каждой группы одно значение. Целое, чётное; от 16px — кратное 4.
3. Для каждой ступени укажи роль: за что она отвечает. Ступень без понятной роли — кандидат на удаление.
4. Покажи мне таблицу «было → предлагаю → роль → где используется → сдвиг в px».
5. Задай вопросы по спорным местам, каждый с вариантами и твоей рекомендацией:
   - две ступени слишком близки — какую оставить;
   - значение встречается один-два раза — это отдельная ступень или ошибка генератора;
   - одна роль в разных блоках имеет разные значения — к какому приводим;
   - округление сдвигает значение больше чем на 2px.
6. Жди моих ответов. До них шкалу в токены не записывай.
7. После подтверждения запиши шкалу в `src/styles/tokens.css`. Дальше в проекте используются только её ступени.

Ориентир по размеру: радиусов — 4–6 ступеней плюс pill, размеров шрифта — 8–12 ступеней. Получается больше — значит, группировка недостаточна, предложи, что объединить.

# Этап 3. Типографика

Шкала размеров шрифта собирается из выгрузки по порядку из раздела «Как собрать шкалу». Требования к итоговой шкале:

- только целые чётные значения, от 24 и выше — кратные 4;
- у каждой ступени есть роль (дисплей, заголовок секции, заголовок карточки, основной текст, подпись и так далее) и имя по роли: `--text-h2-size`, а не `--text-32`;
- одна роль — один размер во всех блоках. Заголовки секций одинаковы по всей странице;
- для каждой ступени заданы значения на десктопе и на мобильном, оба из шкалы;
- размеры, которые отличаются на 1–2px и играют одну роль, объединяются.

Межстрочный интервал подбираем так, чтобы в пикселях он попадал на 4px-сетку. Ориентир: для текста до 20px — около 1.4–1.5 от размера, для заголовков — около 1.1–1.25. Например: 14 → 20, 16 → 24, 20 → 28, 32 → 40, 48 → 56, 64 → 72. Интервалы предложи в той же таблице, что и размеры.

Пиши line-height числом без единиц там, где результат целый (16/24 → 1.5), иначе — в px. Дробных вычисленных значений быть не должно.

Насыщенность — числом: 400, 500, 600, 700. Никаких bold/normal, никаких 350/450. Межбуквенный интервал — единственное место, где дробь допустима (-0.02em): на сетку он не влияет.

Запрещено:

- clamp() и любая fluid-типографика — **кроме плавных ролей** (см. «Плавные и дискретные роли» ниже, п.4). Для дискретных ролей разные размеры делаются медиазапросами, в каждом брейкпоинте значение из шкалы;
- модульные шкалы с коэффициентом (1.25^n, 1.333^n) и rem-значения вида 1.953rem;
- вычисляемые размеры: calc(), font-size в процентах, em от родителя с нецелым результатом.

Исключение (утверждено при приёмке Header 4.0): `clamp()` допустим для **отступов, зависящих от высоты окна** (`vh`), если так сделано в выгрузке. Границы `clamp()` — значения шкалы отступов. Пример: промежутки полноэкранного меню `--menu-gap: clamp(var(--space-32), 5vh, var(--space-64))`.

Оформи типографику переиспользуемыми классами:

```css
.text-h1 { font-size: 32px; line-height: 40px; font-weight: 600; }
```

В разметке ставим класс, а не переопределяем размер внутри каждого компонента.

Шрифты: только Unbounded и Mulish, локальные `woff2` с подмножествами latin и cyrillic, `font-display: swap`, предзагрузка начертаний первого экрана. Никаких системных стеков вида -apple-system в качестве основного шрифта и никаких подключений с Google Fonts.

# Этап 4. Токены

Всё вышеперечисленное оформи как CSS-переменные в `:root` с осмысленными именами: `--space-8`, `--radius-md`, `--control-h-md`, `--color-*`, `--text-h1-size`, `--text-h1-lh`. Туда же — длительности и кривые анимаций: `--dur-fast`, `--dur-base`, `--dur-slow`, `--ease-out`.

**Шрифтовые токены — поэтапно (решения п.6–10).** Сейчас заводим в токенах только роли, нужные для первых шести блоков (Header, Footer, Hero, Stats, Season, Worlds). `font-size` и `line-height` берём из рендера как есть, без сведения ролей между собой. Имена ролей — из Системы А, где подходят (`accent-15` переименован в `body-sm`, `label-xs2` → `label-2xs`); у Hero и Worlds две отдельные роли — `h1` (108) и `display` (96), к 104 не сводить. Токены помечаются `/* временные, до прогона унификации */`. Размеры из остальных блоков (36, 44, 48, 76, 80 и прочие) в токены не вносим до вёрстки их блоков. После вёрстки шести блоков — отдельный прогон унификации (см. `docs/ROADMAP.md`).

**Плавные и дискретные роли (п.4–6).**

- Если значение роли в рендере на 1440 и на 1920 отличается больше чем на 2px — роль **плавная**: в токене остаётся формула `clamp()` из выгрузки как есть (десктоп ≥768), мобильное значение (<768) — из рендера на 390. Такие роли: `h1`, `display`, `decor`, `stat`, `stat-lg`, `stat-sm`, `lead` в Hero (и все прочие, попадающие под критерий). Исключение: `stat-sm` в рендере задан как `em` от `stat-lg` (не `clamp`) — переносится как есть.
- **Потолок плавной роли = рендер на 1920.** Верхняя граница `clamp()` равна значению роли в рендере на 1920, а не потолку из выгрузки: страница ограничена шириной 1920, и на более широких экранах текст не растёт. Нижняя граница и наклон `vw` остаются как в выгрузке. Если потолок выгрузки уже достигается до 1920 (рендер на 1920 = потолок), формула не меняется. Пример: Hero `h1` `clamp(30px,5.6vw,144px)` → `clamp(30px,5.6vw,108px)`.
- Остальные роли — **дискретные**: четыре значения по ступеням (`≥1600` с 1920, `1280–1599` с 1440, `768–1279` с 1024, `<768` с 390), медиазапросами, без `clamp()`.
- Одноимённые роли в разных блоках не сливаем молча. Расходятся на любой ступени на 1px → берём более частое значение. Больше 1px → это разные временные роли с разными именами (например, `body`: Footer 17 на мобильном vs Stats 14; на время — разные токены).

**Цвета (п.12–16).**

- **Примитивы** называются одним словом в стиле палитры (`spruce`, `forest`); два разных цвета не делят одно слово. Новые примитивы из рендера: `sage` #9dbaaa, `clay` #c9bbae, `pine` #2f5a48, `moss` #3a4a3c, `linen` #f7f2e8, `ash` #2b2e2d. Ролевые токены (`--bg-field`, обводка иконок, заливка точек, фон `:disabled`) **ссылаются на примитивы**, а не на hex.
- Цвет вне палитры: `ΔE < 3` до ближайшего токена (включая новые примитивы) → слить; иначе добавить примитивом. Так `#f4f1ea` → `linen` (ΔE 1.74), `#2b2e2d` → отдельный примитив `ash` (ΔE 8.98).
- **Стоп-цвета градиентов отдельными токенами не заводим.** Градиент — один токен целиком, со значениями из рендера.
- Список «меньше 5 раз»: `ΔE < 3` — слить; остальные показываем при вёрстке блока, где встречаются. Цвета мока Dashboard и дефолты нативного `<select>` не учитываем.
- **rgba-подложки (скримы/вуали):** имена можно взять из Системы А, значения и прозрачность — только из рендера. Рендер использует больше ступеней α и больше базовых цветов, чем Система А (белый, чёрный, night-bark, sea-wave) — расхождения в отчёте аудита.
- **Чёрные `rgba(0,0,0,α)` на spruce не заменяем** цветами бренда: брендбук в проекте не используется, источник истины — рендер. Допустимо слить чёрный с базой `night-bark` при той же α. Ступени α, отличающиеся не больше чем на 0.03, можно сводить в одну; остальные оставляем как в рендере.

В компонентных стилях — только var(), никаких магических чисел.

После моего подтверждения маппинга `src/styles/tokens.css` становится единственным источником значений; страница `/styleguide/` показывает их наглядно.

# Этап 5. Разметка

- Один логический блок — одна обёртка. Убери div-пустышки и лишние вложенности от генератора.
- Семантика: header/nav/main/section/article/aside/footer/ul/li/button/a. Один `h1` на страницу, заголовки без пропуска уровней.
- Раскладка только на flex/grid с gap. Отступы между элементами — gap, а не margin у соседей.
- Отступы и выравнивание — логическими свойствами (`padding-inline`, `margin-block`, `inset-inline-start`, `text-align: start`), чтобы письмо справа налево включалось без переписывания.
- position: absolute — только для настоящих наложений (бейджи, оверлеи, текст поверх фото). Всё остальное на потоке.
- transform/translate для раскладки не используем. transform — только для анимаций.
- У блоков с текстом нет фиксированных высот и `overflow: hidden` ради обрезки: текст на другом языке должен помещаться.
- Псевдоэлементы `::before`/`::after` — только для чистого декора. Текста и значимых иконок в них нет.
- Иконки — инлайновые `<svg>` с viewBox и `currentColor`. Никаких иконочных шрифтов и background-image для иконок.
- Контентные картинки — компонент изображения Astro: AVIF, несколько ширин, `width`, `height`, `alt` из Sanity. background-image только для настоящих декоративных фонов.
- Текста в картинках нет. Если в выгрузке текст зашит в изображение — вынеси его в разметку и сообщи.
- Текст цельными узлами: заголовок = один элемент. Не разбивай строку на span-ы ради стилей. Разбиение на строки или слова для анимации делает JS в момент запуска, а исходный текст остаётся доступен скринридеру.
- Повторяющиеся блоки (карточки, пункты списка, ячейки) — один компонент Astro, который рендерится из массива Sanity. Строго идентичная структура и одинаковые классы.
- Классы по смыслу, BEM: `.apartment-card__price`, а не `.flex-row-2`. Никаких сокращений и хешей. Scoped-стили Astro не используем.
- Ни одного текста, пути к файлу, телефона и ссылки в разметке: всё приходит из Sanity.

# Этап 6. JS и анимации

Переносим то, что есть в выгрузке, один в один: те же элементы, те же триггеры, те же длительности и кривые из таблицы аудита. Новых анимаций, ховеров и эффектов не добавляем.

**Разделение.** Логика интерфейса и анимации лежат в разных модулях:

- `src/scripts/ui/` — меню, попапы, табы, аккордеон, слайдеры;
- `src/scripts/form/` — проверка полей, отправка, UTM. Отдельно от анимаций и от остального интерфейса;
- `src/scripts/anim/` — общее ядро и по одному файлу на блок: `anim/blocks/<блок>.js`.

**Модуль анимации блока.** Экспортирует `init(root)` и возвращает функцию очистки. Работает только внутри своего `root`, не ищет элементы по всему документу. Элементы помечаются атрибутами `data-anim="..."`, а не классами стилей.

**Запуск.** Ядро следит за блоками через IntersectionObserver и подгружает модуль блока динамическим импортом, когда блок подходит к экрану. GSAP и ScrollTrigger загружаются один раз. Первый экран инициализируется сразу, без ожидания.

**Что можно анимировать (решение Р6).**

- разрешены `transform`, `opacity`, `clip-path`, `stroke-dashoffset`;
- анимации `width` / `height` / `left` / `top` / `flex-grow` / `letter-spacing` переписываются на `transform` (FLIP) с тем же видом;
- `filter` (blur, grayscale) в движении — только в анимациях по клику или ховеру, не в скролл-сценариях;
- раскрытие FAQ через `grid-template-rows` оставляем как есть;
- всё, что не укладывается в этот список, показываешь мне поблочно на этапе 6 до переноса.

**Без JS контент виден.** Скрытые стартовые состояния (opacity: 0, сдвиг) задаёт только JS. В CSS нет правил, которые прячут контент в ожидании анимации. Исключение — первый экран: его стартовое состояние можно задать через класс `js` на `<html>`, чтобы не было мигания.

**`prefers-reduced-motion`.** Анимации появления и скролла не запускаются, всё показано в конечном состоянии. Логика интерфейса работает как обычно.

**Скролл.** Плавный скролл, перехват колёсика и привязка видео к скроллу — только если это есть в выгрузке. `ScrollTrigger.refresh()` вызывается после загрузки шрифтов и после смены размеров окна. У всех фото заданы размеры, чтобы точки срабатывания не съезжали.

**Производительность.**

- В обработчиках скролла и в каждом кадре нет чтения размеров (`getBoundingClientRect`, `offsetHeight`). Размеры читаются один раз и при изменении окна.
- Слушатели скролла и касаний — `passive`.
- `will-change` ставится перед анимацией и снимается после.
- Тяжёлые эффекты (`backdrop-filter`, `filter`) не анимируются.
- Длительности и кривые берутся из токенов: один файл констант в JS повторяет значения из `tokens.css`.

**Доступность интерфейса.** Меню и попапы запирают фокус, закрываются по Esc и возвращают фокус на кнопку открытия. Табы и аккордеон управляются с клавиатуры, состояния отражены в `aria-*`.

# Приёмка блоков (решения п.18–20)

Правила упрощены после приёмки Header (2026-11-16):

- **Попиксельная сверка** с `design-export/index.html` — только на **1920, 1440 и 390**: пары скриншотов, дифф, замеры элементов.
- **1280, 1024 и 360** — по одному скриншоту вёрстки без диффа: проверка «ничего не сломалось» (ничего не вылезает, не обрезается, не наезжает).
- **1600 и 1680** больше не проверяем.
- **`en` и строки на 40% длиннее** — только на **1440 и 390**.
- **Отчёт по блоку:** пары скриншотов и список только тех элементов, где отклонение больше 2px или изменилось число строк. Полные таблицы по элементам не нужны. Блок не готов, пока человек не посмотрел сравнение.
- Если значение в токенах не встречается в рендере (кроме округления до 2px по шкалам и правил «Диапазоны и контейнер»), не добавляй его без подтверждения человека (п.20).

Скриншоты снимаются headless-браузером (Playwright Chromium), который используется и для аудита. См. «Среда» в `docs/ROADMAP.md`.

## Запуск сравнения

Скрипт `scripts/acceptance/compare.mjs` (Playwright из devDependencies, браузер — из `/opt/pw-browsers` контейнера).

```sh
npm run build
npm run acceptance -- --block hero                    # сверка 1920/1440/390 + скриншоты 1280/1024/360
npm run acceptance -- --block hero --lang en --widths 1440,390 --smoke none   # en: только 1440 и 390
npm run acceptance -- --block hero --widths 1440 --states winter --smoke none --url http://localhost:4321
```

| Параметр | Значение |
|---|---|
| `--block` | имя конфига `scripts/acceptance/blocks/<блок>.mjs`, обязательно |
| `--widths` | ширины попиксельной сверки через запятую; по умолчанию `1920,1440,390` |
| `--smoke` | ширины «ничего не сломалось» — только скриншот вёрстки, без диффа; по умолчанию `1280,1024,360`, `none` — пропустить |
| `--states` | состояния из конфига через запятую; по умолчанию все |
| `--lang` | язык вёрстки, по умолчанию `uk`. Выгрузка только на украинском: с `en` сравнение показывает поведение длинного текста, а не совпадение |
| `--url` | адрес запущенного сервера; без него скрипт сам раздаёт `dist/client` |
| `--out` | папка результатов; по умолчанию `.acceptance/<блок>[-<язык>]/` (не в git) |

Результат: `<ширина>-<состояние>-exp.png` (выгрузка), `-ours.png` (вёрстка), `-diff.png` (несовпавшие пиксели красным), `<ширина>-<состояние>-smoke.png` (проверочные ширины), `report.json` с замерами. В консоль — процент несовпавших пикселей и только элементы, разошедшиеся больше чем на 2px по позиции или размеру или по числу строк; на проверочных ширинах — элементы, вылезающие за окно по горизонтали.

Новый блок = новый конфиг в `scripts/acceptance/blocks/` по образцу `header.mjs`: CSS, который прячет в выгрузке и вёрстке всё, кроме блока; состояния (как довести страницу до состояния, область скриншота, на каких ширинах оно есть); пары селекторов «выгрузка ↔ вёрстка» для замера.

# Этап 8. Структура проекта

```
src/
  components/
    blocks/<Блок>.astro      один блок лендинга
    ui/<Компонент>.astro     кнопка, поле, карточка, тег
  layouts/Base.astro
  pages/[lang]/index.astro
  pages/styleguide.astro
  styles/
    tokens.css  reset.css  typography.css  layout.css
    components/<имя>.css
    blocks/<имя>.css
    main.css                 импортирует всё
  scripts/
    ui/  form/  anim/
  lib/                       запросы к Sanity, языки
studio/schemas/blocks/<блок>.ts
```

- Один компонент — один файл стилей и одна схема Sanity с тем же именем.
- Никаких style-атрибутов в разметке. Исключение — CSS-переменная со значением из Sanity (например, позиция фокуса фото).
- CSS без препроцессоров и без утилитарных фреймворков.
- Сборка проходит без ошибок и предупреждений.
